# StudyRequest Model Documentation

## Overview

The `StudyRequest` model represents a study access request submitted by an external researcher or Data Portal to the Consent Management Service.

It stores both:

1. Operational information used by the Consent Management Service.
2. The complete descriptive content of the study request received from the external system.

The request starts in a `PENDING` state and remains pending until all required hospitals approve it. A single rejection closes the request immediately. If the review deadline passes while one or more hospital decisions are still pending, the request becomes `EXPIRED`.

---

## Main Responsibilities

The `StudyRequest` model is responsible for:

- identifying the request inside the Consent Management Service;
- linking the request to the original study in the external system;
- linking the request to the researcher who submitted it;
- storing the complete request payload;
- storing the applicant signature information;
- tracking the current request status;
- tracking submission, expiration and resolution dates;
- supporting the future relationship with hospital decisions.

---

## Identifier Distinction

The model contains three different identifiers.

### `id`

Internal database primary key.

It is used by Sequelize and by foreign-key relationships with other database entities.

Example:

```text
27
```

This value does not need to be exposed in external API responses.

### `requestId`

Identifier generated by the Consent Management Service.

It identifies the consent approval workflow inside this component.

Example:

```text
req_2026_0001
```

### `studyId`

Identifier of the study in the external Data Portal or source system.

It allows the external platform to correlate its study with the approval process managed by the Consent Management Service.

Example:

```text
study_2026_0001
```

Example record:

```json
{
  "id": 27,
  "requestId": "req_2026_0048",
  "studyId": "study_2026_0001"
}
```

## Fields

| Field | Type | Required | Description |
|---|---|---:|---|
| `id` | Integer | Yes | Internal database primary key. |
| `requestId` | String | Yes | Unique request identifier generated by the Consent Management Service. |
| `studyId` | String | Yes | Identifier of the study in the external system. |
| `formType` | Enum | Yes | Type of study access request. |
| `title` | String | Yes | Human-readable study title. |
| `language` | String | Yes | Submission language in ISO 639-1 format. |
| `status` | Enum | Yes | Current overall request state. |
| `researcherId` | Integer | Yes | Foreign key referencing the researcher who submitted the request. |
| `requestPayload` | JSONB | Yes | Complete descriptive content of the study request. |
| `signatureAlgorithm` | String | Yes | Algorithm used to produce the applicant signature. |
| `signedPayloadHash` | Text | Yes | Hash of the exact payload that was signed. |
| `signatureValue` | Text | Yes | Digital signature received with the request. |
| `signedAt` | Date | Yes | Date and time at which the payload was signed. |
| `submittedAt` | Date | Yes | Date and time at which the request was accepted by the service. |
| `expiresAt` | Date | Yes | Deadline for hospital decisions. |
| `resolvedAt` | Date | No | Date and time at which the request reached a final state. |
| `createdAt` | Date | Yes | Sequelize creation timestamp. |
| `updatedAt` | Date | Yes | Sequelize update timestamp. |

## Form Types

The current model supports:

```text
DATA_REQUEST
DATA_ACCESS_APPLICATION
```

`DATA_REQUEST` represents a request involving aggregated data.

`DATA_ACCESS_APPLICATION` represents an application involving personal-level data.

## Request Lifecycle

### `PENDING`

The request has been submitted, but one or more hospitals have not yet provided their decision.

This is the default state.

### `APPROVED`

Every required hospital has approved the request.

The request is resolved and `resolvedAt` must be populated.

### `REJECTED`

At least one hospital has rejected the request.

A single rejection immediately closes the process, even when other hospitals have not yet responded.

The request is resolved and `resolvedAt` must be populated.

### `EXPIRED`

The review deadline has passed while one or more hospital decisions are still pending.

The request is resolved and `resolvedAt` must be populated.

## Researcher Relationship

Each study request belongs to exactly one researcher.

One researcher can submit multiple study requests.

```text
Researcher 1 ---- N StudyRequest
```

The foreign key is:

```text
StudyRequest.researcherId -> Researcher.id
```

Sequelize association:

```javascript
StudyRequest.belongsTo(models.Researcher, {
  foreignKey: "researcherId",
  as: "researcher",
});
```

The inverse association in the `Researcher` model is:

```javascript
Researcher.hasMany(models.StudyRequest, {
  foreignKey: "researcherId",
  as: "studyRequests",
});
```

---

## Public Key Resolution

The researcher's public key is not duplicated inside `StudyRequest`.

The public key is resolved through the researcher relationship:

```text
StudyRequest.researcherId
        |
        v
Researcher.publicKeyId
        |
        v
PublicKey.id
```

Current relationship:

```text
Researcher 1 ---- 1 PublicKey
```

This is sufficient for the current POC.

A future version may store the exact `publicKeyId` used for each request in order to support key rotation and preserve the verification history of older signatures.

## Signature Information

The request stores the information required to verify the applicant signature:

```text
signatureAlgorithm
signedPayloadHash
signatureValue
signedAt
```

### `signatureAlgorithm`

Describes how the specific signature was produced.

Examples:

```text
ES256
RS256
ECDSA_SHA256
```

This is different from the generic key algorithm stored in `PublicKey`, although the two values must be compatible.

### `signedPayloadHash`

Contains the hash of the exact payload that the researcher signed.

The backend should recalculate the hash from a canonical representation of the request payload and compare it with this value before verifying the signature.

### `signatureValue`

Contains the actual digital signature.

### `signedAt`

Records when the signature was produced.

## Hospital Decision Relationship

Each study request will create one decision record for every hospital whose datasets are involved.

Expected relationship:

```text
StudyRequest 1 ---- N HospitalDecision
```

Future association:

```javascript
StudyRequest.hasMany(models.HospitalDecision, {
  foreignKey: "studyRequestId",
  as: "hospitalDecisions",
});
```

The overall `StudyRequest.status` will be calculated from the related hospital decisions.

Expected rules:

```text
All hospitals approved  -> APPROVED
One hospital rejected   -> REJECTED
Pending decisions remain -> PENDING
Deadline passed         -> EXPIRED
```

## Implementation Notes

- `resolvedAt` should remain `null` while the request is `PENDING`.
- The service layer should populate `resolvedAt` when the request becomes `APPROVED`, `REJECTED` or `EXPIRED`.
- The service layer should generate `requestId`.
- The service layer should calculate `expiresAt`.
- The service layer should verify the request signature before creating hospital decision records.
- The service layer should create one `HospitalDecision` for every requested hospital.
- Database state must be updated before publishing notification events to RabbitMQ.
- RabbitMQ should communicate state changes but should not be the source of truth for request status.
